# 决策台账、管理界面与插件管理

这里的"审计"指的是**决策台账**——机器人每次判断留下的可追溯记录，以及管理界面自己的 HTTP 接口。
系统**不记录也不审计出站 HTTP 请求**：没有请求日志、没有 HTTP 层拦截器。要约束机器人对外发出什么请求，
只有两条途径，见 [两类过滤插件](RISK_FILTERS.md)：

| 途径 | 管什么 |
| --- | --- |
| 业务风控插件 | 每一次市场 API 调用，含只读 |
| Agent 行为风控插件 | 模型发起的每一次工具调用，其中一部分会发出 HTTP 请求 |

运行：

```bash
.venv/bin/prediction-market-agent serve
```

本地默认打开 `http://127.0.0.1:8765`；容器部署可在程序配置中监听 `0.0.0.0`。

## 决策可解释性

专用 `decision_ledger` 每行代表一次 outcome 决策，并用 `decision_id` 关联 Provider 轮次、Agent 工具步骤
和执行动作。页面的“决策台账”拉通显示：

- 当时的标准化市场、盘口、持仓、API 能力和策略版本；
- 每个研究工具的参数、结果与错误；
- 模型原始输出和结构化提案；
- Agent 行为风控的允许、缩减、拒绝或停止原因（`risk_decision` 字段）；
- 业务风控的拒绝理由：以执行失败的形式出现在 `execution` 里，状态为 `EXECUTION_ERROR`，原因字符串保留
  插件给出的理由。它**不写入** `risk_decision`——该字段只记 `agent:actions` 一路；
- 额度不足导致没下单时，动作层单独记为 `BUY_REJECTED`，`result.status` 为 `RISK_REJECTED`；
- 最终动作及远端执行响应/失败；
- 同 token 后续决策快照中的初始/最新 midpoint 与变化，或明确显示尚无后续观察。

可按 platform、provider、status、action 筛选，便于比较 Provider、策略文件哈希、风控调整和后续市场表现，
持续优化策略插件。原始完整记录仍可单独查询，不会只保留页面摘要。

浏览器中的逻辑操作仍使用 `/api/summary`、`/api/decisions`、`/api/records`、`/api/manifest`、
`/api/plugins/manage`、`/api/runtime` 和 `/api/settings` 等稳定名称，但不会直接发这些明文 URL 请求。登录后页面把逻辑 URL、
参数和正文一起放进 AES-GCM 信封，统一提交到 `POST /api/secure`，服务端解密分派后再加密响应。
回环或明确私网 IP 地址页面则通过 `POST /api/local` 发送明文 JSON `{ "url": "/api/settings", "body": null }`，无需会话、
Passkey 或加解密；写操作使用相同封装并在 `body` 中提供字段。两条通道复用同一业务分派逻辑。

## 插件管理

页面动态管理七类插件。Decision Provider 集中显示在“模型服务”，其余六类显示在“插件中心”；禁用项只显示文件名和来源，启用项调用初始化后显示描述、存储说明及字段表单。
秘密不回显。程序字段、插件目录、启用状态和插件字段都支持保存及删除/恢复：

- `/api/settings`、`/api/settings/reset`
- `/api/plugins/selection`
- `/api/plugins/directories`、`/api/plugins/directories/reset`
- `/api/plugins/config`、`/api/plugins/config/reset`、`/api/plugins/config/delete`
- `/api/plugins/install`
- `/api/plugins/refresh`
- `/api/plugins/controls`、`/api/plugins/controls/action`
- `/api/plugins/config/choices`
- `/api/runtime`、`/api/runtime/control`
- `/api/auth/manage`、`/api/auth/passkeys/*`、`/api/auth/sessions/kick`

非本地地址访问的管理操作要求有效的 HttpOnly 会话 Cookie、会话请求 token 和 ECDH 派生密钥。保存配置时插件系统只调用
插件的 `save_callback` 或 `delete_callback`。刷新会卸载旧注册表并按磁盘最新状态重建。完整认证和信封协议
见 [AUTHENTICATION.md](AUTHENTICATION.md)。

“机器人运行控制”显示 AI 主链 readiness、每个平台自己报告的启动原因、暂停和 runtime/事件队列状态。
全局或逐平台暂停写入 `management_file` 并立即执行启停；恢复后只有插件报告可启动的平台会启动。安装新插件时，页面提交
类别、目标目录、名称和源码；服务端校验后写入，不覆盖已有文件，新文件默认禁用。

## 账本分三个标签

一行记录可能是三种东西之一,而它们回答的是三个不同的问题。混在一起,三个都答不好 —— 想看"它决定了什么"
的人不需要翻过一百条模型超时,排查故障的人也不想在一堆正常决策里找那几条失败。

| 标签 | 里面是什么 | 能删吗 |
| --- | --- | --- |
| **有结论**(默认) | 得出了结论的判断:观望、买入、卖出、规则拒绝 | 能 |
| **分析中** | 模型正在跑,还没有结论 | **不能**(运行中的代码还要把结论写回去) |
| **出错** | 没能得出结论:模型调用失败、执行失败 | 能 |

规则拒绝算**有结论**不算出错 —— 什么都没坏,是过滤插件被问到并且说了不行,那是一个结果。

分组只在一处定义(`SessionMemory.decision_group`),而且**在 SQL 里过滤**:否则"给我一百条有结论的"会
变成"最近一百条里碰巧有结论的那几条"。每个标签的计数单独查,因为从当前页面的行数里数,只能数出屏幕上
有几条。

## 删除决策记录

账本里的条目不只是历史，它们**参与将来的判断**：结算后的决策用来校准策略的概率估计，模型往返的成败用来
排 provider 的先后，历史决策会被召回进下一次提示词。所以一条因为已修复的故障而失败的记录，不是"看着乱"，
它会继续拿一件不再成立的事影响行为。

因此每条决策旁边有「删除这条记录」，删掉的是这次决策本身、这次的模型往返和工具步骤。按平台或按状态批量
删走同一个接口（`/api/decisions/forget`），但**不填任何条件会被拒绝**——空筛选等于全表，那种事不该由留白
得到。

**正在进行中的决策删不掉。** 状态是 `STARTED` 的那一行,正被运行中的代码持有,它还要回来把结论写进去。
删掉之后那次写入会 UPDATE 到一个不存在的行 —— 而匹配 0 行的 UPDATE **不算错误**,于是推理和结论就静默
消失了,而操作员以为自己只是清掉了一条卡住的记录。批量删除会跳过它、把其余删掉,并告诉你跳了几条。

**已经在平台上发生过的动作不会跟着删。** 账户的现金和持仓是独立保存的状态，不是从 `execution_actions`
推出来的；删掉记录余额照旧，账本就会和余额对不上。所以这类决策的删除请求被拒绝，并告诉你它牵连着几条真实
动作。

## AI 不可用时会发生什么

每一轮循环的存在都是为了产生一个决策，而决策需要模型。所有 provider 都限流或掉线时，框架有一个**专门的
可用性循环**在跑，它是此刻唯一该跑的东西——因为它是"什么时候可以恢复"的唯一来源。

它不花钱也不发请求：provider 失败时错误已经被分类、冷却时间已经记下，所以"现在能不能答"是查出来的，不是
再失败一次试出来的。

框架只陈述事实，**停不停扫是插件自己的决定**。事实通过插件 runtime 的 `notify` 通道送达，两个市场插件收到
后暂停自己的事件循环，并在状态里写明在等什么（`holding_because`）；不关心的插件不声明这个回调，就不会被
通知。某个插件在收到通知时出错，不影响其它插件收到；这个监控循环本身也永远不会成为机器人启动失败的原因。

## 纸面交易模式

判断这台机器人值不值得托付,只能看它跑起来的样子:它挑什么标的、怎么推理、提议什么交易。而正常情况下
看到这些的前提是先往钱包里打钱 —— 在还不知道它值不值得打钱之前。

开了这个模式(应用设置 `paper_trading`),**除了真正的买卖,一切照旧**:真实平台、真实价格、真实模型、
真实账本、真实结算判定。只有订单停在门口,按平台**当时报出的价格和费率**在本地成交,持仓、现金和已实现
盈亏照常记账。标的揭晓后按平台给出的真实胜负结算,所以你能看到"如果当初真买了,现在赚赔多少"。

| 这一层做什么 | 为什么 |
| --- | --- |
| 报价照样问平台 | 猜价格会让后面每个数字都是虚构 |
| 成交价就是报价、费率就是报的费率,**不会更好** | 按你想要的价格成交的模拟器,是一台生产好看数字的机器 |
| 可用金额用你填的模拟数,`source` 标成 `simulated` | 唯一会让这个模式变得有害的失败,是把模拟结果当成真赚到的钱 |
| 平台真实余额并排显示在 `detail` 里 | 让"哪个是钱、哪个不是"一直摆在读的人眼前 |
| 要资金请求:在模拟额度内立即满足,超出则拒绝 | 静默满足任何金额会藏掉最值得看的行为——它拿不到想要的钱时怎么办 |
| 只读、能力声明、结算判定原样透传 | 这些本来就该是真的 |

包装发生在**风控之前**,所以两类过滤插件看到的调用和实盘完全一样 —— 变的只有写操作最终落到哪。

**默认是关的。** 没人打开它,就是实盘。

### 揭晓与结算

只有假设买入、没有后续揭晓,是看不出效果的。这里原先有个缺口:结算只在"已到期的标的恰好又被发现扫到"
时才发生,而交易所列的是**开放**市场,不会列出刚刚关闭的那个 —— 也就是唯一持有未实现结果的那个。于是
仓位会被买入然后永远不结算,账本上停在最后一个标价。

现在每轮开头按**持有的仓位**去查:没到期的花一次读取就返回,到期的按平台的真实胜负结算入账。

Polymarket 这边顺带补了实现 —— 它的 `outcome_won` 原来是个空实现、并声明自己无法报告胜负,所以那边
从来不会结算。Gamma 是说得很清楚的:已结算市场把赢的一面标到 1、输的一面标到 0。判据取"价格已经离开
交易区间",不是"哪边领先" —— 还在 0.97 交易的市场仍然可能是错的,把它当结算会记一笔没发生的盈利。

## 账本怎么加载

之前它在定时器上整页重建,一次拉 100 条 —— 每条都带着完整上下文、研究轨迹和模型原始输出。结果是:打开后
空白很久(看起来像没数据)、读到一半被刷新收起、展开的 JSON 块每次都被折叠。

现在:

| | 做法 | 为什么 |
| --- | --- | --- |
| **不自动刷新** | 顶部一个「↻ 刷新」按钮,旁边写着上次读取时间 | 账本是只写历史,写完就不会变;定时重建只会让读的人丢失位置。旁边明说「这里不自动刷新」,否则一个从不更新的页面和一个卡住的页面分不出来 |
| **分页** | 首屏 10 条,向下滚动每次追加 5 条 | 几乎没人读过前几条以后 |
| **追加而不是重画** | `insertAdjacentHTML('beforeend')` | 重画会把读者展开的面板关掉 |
| **只在向下滚时加载** | 记录滚动方向 | 读者往回翻时,哨兵仍然在视口里——因为有人在往上读就去拉更旧的数据,正好是反的 |
| **骨架屏** | 就放在新行将要出现的位置,形状和真实行一致 | 页面别处的转圈告诉你"有事在发生"但不告诉你"在哪发生",而读者正盯着那个即将被填上的空隙 |
| **往上滚时停掉动效** | 方向一变就清掉骨架屏 | |
| **标签计数在数据库里数** | 三个 `COUNT(*)` | 原来是每个标签拉 200 行再数长度:600 行、三次往返,就为了显示三个数字 |

诊断用的三张表(执行动作、模型往返、工具步骤)也从各 100 行降到各 20 行 —— 它们在折叠面板里,没人展开也照样在拖慢这一页。

骨架屏的动效尊重 `prefers-reduced-motion`:关掉动画后形状本身仍然读得出是占位。

### 真正慢的地方:请求在排队

上面这些都减少了浪费,但**都不是它慢的原因**。实测(浏览器端到端):

| | SQLite 查询 | 解析 30 条完整记录 | 拼 HTML + 渲染 |
| --- | --- | --- | --- |
| 耗时 | < 0.35s | 4ms | 约 25ms |

三样都快。慢的是服务端**把请求一个一个串行处理**:`/api/settings` 单独调 3ms,和页面其它请求一起到达时要
616ms。原因是控制台的 handler 全是同步代码(查库、调插件、拼 JSON),而只有四个路径被放进了线程池 ——
其余所有请求都直接跑在 asyncio 事件循环上,跑的时候整个循环被占住,别的请求只能等。

现在所有请求都走线程池,加密通道的整包加解密也是。之所以现在可以这么做,是因为数据库连接已经改成按线程
各持一个(见上文),handler 不再有跨线程的共享连接。

这一条有**行为测试**守着,不是查源码字符串:故意让一个接口慢 0.6 秒,并发打三个请求,要求总耗时小于
1.2 秒。改回旧写法时它实测跑出 1.82 秒并失败。

### 点开一条才取完整证据

列表行不再带模型拿到的完整上下文和模型原始输出 —— 10 条里这两样占了 94%(308 KB + 179 KB),而列表只画
一个标题和一句理由。点开某一条时才调 `/api/decisions/detail` 取完整记录并重画那一条。打开页面的总负载
从约 3 MB 降到 141 KB。

三张诊断表(平台操作、模型对话、信息收集)在标着「排查问题时展开」的折叠面板里,原来每次打开页面都照拉
(模型对话和信息收集 20 条就各有 1 MB 以上),现在展开面板时才加载。
