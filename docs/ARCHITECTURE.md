# 架构与边界

机器人由通用编排内核和六类自动扫描插件组成：API、决策 Provider、决策策略、研究工具、风控、Hook。
插件系统只负责目录发现、启用顺序、JSON schema 验证、配置回调调用和生命周期，不包含平台名、凭证、URL、
代理、资金数字、损益公式、网络白名单或策略内容。

## 源码布局

- `core/`：通用运行配置、领域模型、账户状态持久化、Hook 与风险协议。
- `plugin_system/`：插件契约、自动发现、生命周期、启用状态和配置回调。
- `agent/`：Provider 决策协议、多步研究工具协议和文本策略协议。
- `runtime/`：启动装配、市场评估、动作执行、循环引擎、SQLite、报告、Passkey/ECDH 与 Web 界面。
- `plugins/`：按 `api`、`providers`、`strategies`、`research`、`risk`、`hooks` 六类组织的内置插件。

Binance 与 Polymarket 的配置、读取和写入实现分别位于 `plugins/api/_binance/` 和
`plugins/api/_polymarket/`；插件系统不引用这些平台目录。

## 一次决策的数据流

1. API 插件读取自己的平台，把事件、市场、outcome、盘口、K 线和能力差异标准化。
2. 策略插件按自己的状态、outcome 和流动性配置选择候选，并从私有配置指定的文本文件加载策略。
3. 内核组合市场、持仓、API 能力、风险清单、策略文本和历史窗口。
4. Provider 按有序列表接管同一个多步 Agent；研究工具插件动态贡献工具名、说明和执行器。
5. Agent 可反复收集网页、来源、跨市场、行情或历史证据，再生成结构化提案。
6. 风控协调器调用命名目标规则；插件可以允许、缩减、拒绝或停止动作；没有适用规则时内核不额外增加政策。
7. 执行网关调用 API 插件的线上写传输。系统没有本地撮合或执行模式分支。
8. Hook 包围 Agent 和交易动作；SQLite 决策台账关联上下文、证据、提案、风控、执行和后续观察。

`SEARCH_MARKETS` 只提供候选。不同平台是否描述同一事件、能否共享外部证据、结算条件是否一致，均由
Agent 根据各 API 插件的原始规则和能力清单判断；内核不以标题相似度替代语义决策。

## 平台差异

通用写接口使用标准化计价金额/份额字符串，不包含链上精度。Binance 插件内部转换其接口单位并签名；
Polymarket 插件内部处理 pUSD 精度、CLOB 凭证、钱包签名和 Relayer。平台原始订单状态也由对应插件
归一化，通用网关只接受标准状态。API 能力清单只声明真实实现的
功能；例如无法可靠确定结算赢家的插件会把 `settlement_status` 声明为 false，而不是返回猜测。

本地 `AccountState` 是已确认响应的运行时镜像和风控输入，不是撮合器。只有远端成功响应后才更新；开放
限价单不会因本地盘口穿价而被自行标记成交。

## 会话边界

Codex 和 Claude 客户端可以维护自己的登录信息，但机器人把每次调用视为可替换 Provider。跨轮业务会话
统一存入 SQLite，所以 Provider 故障转移后仍能召回同一市场历史。子进程只继承运行所需的 OS/客户端
环境，不继承其他插件的私有配置。

管理会话与 Agent 业务记忆相互独立：`auth_db` 保存 admin Passkey、公钥签名计数观测值（仅诊断）、挑战、ECDH 会话和
防重放 nonce；`session_db` 保存 Agent 输入输出和决策台账。两条数据库路径先由应用配置解析，再初始化
任何持久层。登录后的业务数据经统一加密分派端点进出，认证引导端点不暴露业务内容。
